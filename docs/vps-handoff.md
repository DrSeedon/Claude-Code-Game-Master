## МЕХАНИКА ПЕРЕЕЗДА (то, что стоило дня выяснений)

- **Инструмент — `scripts/migrate_agent.py`** в репозитории Orchestra. Переносит сессию
  ВМЕСТЕ с транскриптом, логами, inbox и worktrees. Делает `UPSERT`, поэтому работает и
  когда на целевом хосте сессии нет.
- **Руками в `orchestra.db` не лезть.** §6 онбординг-доки описывает противоположную задачу —
  сброс уже существующей протухшей сессии. Живой сервер держит сессии в памяти и молча
  откатит твой `UPDATE`; `save_session()` доставляет ~20 умолчаний, которые руками не
  воспроизвести.
- **Оркестратор не может мигрировать сам себя** — `assert_idle` (migrate_agent.py:144)
  считает вызывающего `running`. Запускает кто-то снаружи. Гейт смотрит только на сторону
  `--from`, поэтому агенты на VPS переезду не мешают.
- **MCP выдаются пер-сессионно** через поле `mcp_servers_custom` в БД, а НЕ через
  `~/.claude.json` (у `kesha` он пустой и должен таким остаться). `orchestra`-MCP вшивается
  автоматически, просить его не нужно.
- **Рестарт Orchestra на VPS не трогать никогда** — рвёт активные ходы всех агентов, включая
  чужие проекты. Этим владеет `Orchestra-orchestrator`.
- **Дашборд 8888 закрыт наружу** (ufw). Только `https://orchestra.seedon.ru`, либо
  `127.0.0.1:8888` изнутри VPS. В нашем проекте зашитых ссылок на 8888 нет — проверено.

Команда миграции (запускает юзер с ноутбука, сначала с `--dry-run`):
```bash
cd /mnt/data/Projects/Python/orchestra && uv run python scripts/migrate_agent.py \
  --name Claude-Code-Game-Master-orchestrator \
  --from maxim@localhost --to root@158.220.127.161 \
  --from-orchestra /mnt/data/Projects/Python/orchestra \
  --to-orchestra /home/kesha/orchestra \
```

## ЧТО ЗНАТЬ ПРО ПРОЕКТ (не потеряй)

- Живые данные **не в git**: `world-state/campaigns` (13 кампаний), `world-state/usage`,
  `.env`. Они существуют только на VPS. Никаких `git clean` и повторных клонов поверх них
  без бэкапа.
- Деплой теперь: `git push` с ноутбука → `git pull --ff-only` на VPS под `kesha` →
  `systemctl restart dnd-game-master`. **VPS тянет из GitHub, а не с ноутбука** — незапушенный
  `main` означает, что приедет вчерашний код.
- Git на сервере запускать только под `kesha` (`su -s /bin/bash kesha`; `su - kesha` виснет,
  пароля нет). Файлы, принадлежащие root, при `User=kesha` ломают запись в `.git` посреди
  деплоя — и падает это не сразу, а через недели.
- Пароль от сайта и порт — в разделе Deploy в `CLAUDE.md`.
